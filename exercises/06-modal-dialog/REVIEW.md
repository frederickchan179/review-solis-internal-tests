# Review - 06 Modal Dialog

### Dev: Findings

| Pri | Area | Issue | Suggestion |
|-----|------|-------|------------|
| Required | Background scroll | Opening the modal only removes `hidden` on the modal root. The page behind still scrolls with wheel, touch, or trackpad. A user reading the dialog can accidentally scroll the page underneath. That breaks REQUIREMENTS: while open, the page behind must not scroll. | Lock `document.body` overflow (or equivalent) when the modal opens.<br>Restore the previous overflow value when it closes. |
| Required | Clipped content | `.modal__dialog` uses `max-height: 80vh` and `overflow: hidden` with no scroll area inside. On a short viewport, the terms text and form fields are permanently cut off. There is no way to reach the clipped content. REQUIREMENTS: all dialog content must stay reachable by scrolling *inside* the dialog. | Keep the dialog shell at a fixed max height.<br>Put overflow scrolling on an inner body pane so terms and fields stay reachable. |
| Required | Keyboard / focus | There is no Escape handler. Focus does not move into the dialog on open, and Tab is not trapped inside it. Close does not return focus to the button that opened the modal. While open, the page “Open” button stays in the Tab order, so keyboard users can leave the modal without closing it. REQUIREMENTS: fully keyboard operable, and focus must return to a predictable place on close. | Cache the element that had focus before open.<br>Move focus into the dialog, trap Tab inside it, and close on Escape.<br>Restore focus to the opener on close, and mark the background `inert` (or equivalent). |
| Required | z-index | The sticky header uses `z-index: 999`; the modal uses `z-index: 100`. Repro: scroll down, then open the modal → the header sits on top of the dialog. That breaks the “dialog on top” expectation the BRIEF points at in step 3. | Raise the modal stacking context (or lower the header) with clear z-index tokens so the modal always wins while open. |
| Optional | HTML | The email field is placeholder-only: no visible label and no `autocomplete`. Close and Subscribe lack `type="button"`. Terms uses `href="#"`, which jumps to the top of the page. There is an inline `height: 400px` spacer. The custom div modal reinvents behavior that native `<dialog>` already covers. | Add a label plus `autocomplete="email"`.<br>Set Close and Subscribe to `type="button"`.<br>Fix or neutralize the Terms `href`.<br>Move the spacer height into CSS.<br>Prefer native `<dialog>` + `showModal()` for focus, Escape, and backdrop when that is acceptable. |
| Optional | A11y / UX | `aria-modal` without a real focus trap can mislead assistive tech. The Close × hit target is tiny. Terms at 12px gray may fail contrast. There is no `:focus-visible` style, so keyboard focus is hard to see. Subscribe does nothing (dead CTA). | Match `aria-modal` with a real trap, or drop the attribute until a trap exists.<br>Enlarge the Close hit target (≥44px).<br>Raise Terms contrast.<br>Add `:focus-visible`.<br>Wire Subscribe, or mark it out of scope. |
| Optional | JS / CSS | Open and close behavior is split across tiny handlers, so it is easy to miss one step (scroll lock without restore, Escape without trap, and so on). An overlay as a sibling is fine, but later “click outside” logic must not close when the user clicks inside the dialog. CSS property order, naming, and null-checks are uneven; `modalEl.querySelector` throws if `modalEl` is null. | One open/close pipeline: scroll lock → focus in → Escape → trap → restore → unlock.<br>Do not close the modal on clicks inside the dialog.<br>Clean CSS property order on modal rules.<br>Naming: `*El` for nodes, `*Btn` for buttons; null-check queries before use. |

### Author: improve the test

| Pri | Area | Issue | Suggestion |
|-----|------|-------|------------|
| Required | Esc / trap | The BRIEF pushes keyboard use, but REQUIREMENTS never name Escape, focus trap, or return focus to the opener. Interviewers argue whether mouse-only close is enough. Scoring then depends on who runs the room. | Put those three behaviors in REQUIREMENTS explicitly: Escape closes, Tab stays trapped, focus returns to the opener. |
| Required | Clip | On a tall laptop the dialog often still “fits”, so the `overflow: hidden` clip bug is easy to miss on the happy path. Interviewers and interviewees can walk away thinking content is fine. | BRIEF: use a ≤600px height viewport (or pad the terms) so clipping is unavoidable without an inner scroller. |
| Required | Header trap | Sticky header over the modal is a strong intentional stacking bug. Polishing the fixture (raising the modal z-index) would hide the lesson. | Do not clean it up in the fixture; BRIEF step 3 already points at it. |
| Optional | Subscribe | Subscribe is unused and distracts interviewees with nothing useful to probe or score. Time goes into a dead button instead of the modal traps. | Mark Subscribe out of scope, or require a harmless no-op / success handler. |
